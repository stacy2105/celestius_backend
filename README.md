# Celestius Event Registration API

A simple REST API built for the Celestius Backend Team Recruitment Task. It lets students register for the **Backend Development Workshop** and lets organizers view registrations.

## Event details

- **Event:** Backend Development Workshop
- **Date:** 20 October 2026
- **Capacity:** 50 participants

## Features

- Register a student using their name and email.
- Optionally save college or department.
- Automatically record the registration timestamp.
- Prevent duplicate registrations using the email address.
- Reject new registrations when the event reaches 50 participants.
- List all registrations.
- Retrieve one registration by its ID.
- Check capacity and remaining seats.
- Store data persistently in SQLite.

## Tech stack

- **Node.js** — JavaScript runtime
- **Express** — HTTP server and API routes
- **SQLite** — lightweight local database
- **better-sqlite3** — SQLite driver

## Requirements

Install **Node.js 18 or later**. You can check whether Node.js and npm are installed by running:

```bash
node --version
npm --version
```

## Setup and run

1. Download or clone this repository.
2. Open a terminal in the project folder.
3. Install dependencies:

   ```bash
   npm install
   ```

4. Start the server:

   ```bash
   npm start
   ```

5. The API will run at `http://localhost:3000`.

The SQLite database file (`registrations.db`) is created automatically the first time the server starts. You do not need to create it manually.

## API endpoints

### 1. Register for the event

`POST /register`

Request body (`Content-Type: application/json`):

```json
{
  "name": "Asha Kumar",
  "email": "asha@example.com",
  "collegeDepartment": "Computer Science"
}
```

`collegeDepartment` is optional. The `registered_at` timestamp is generated by the server.

**Success — `201 Created`**

```json
{
  "message": "Registration successful.",
  "registration": {
    "id": 1,
    "name": "Asha Kumar",
    "email": "asha@example.com",
    "college_department": "Computer Science",
    "registered_at": "2026-10-23T12:00:00.000Z"
  }
}
```

The timestamp above is an example; the API returns the actual registration time.

Possible errors:

- `400 Bad Request` — name/email missing, invalid email, or invalid field type.
- `409 Conflict` — email already registered or event is full.
- `500 Internal Server Error` — unexpected server-side error.

### 2. View all registrations

`GET /registrations`

Returns all participants, the current registration count, and the event capacity.

Example response:

```json
{
  "count": 1,
  "capacity": 50,
  "registrations": [
    {
      "id": 1,
      "name": "Asha Kumar",
      "email": "asha@example.com",
      "college_department": "Computer Science",
      "registered_at": "2026-10-23T12:00:00.000Z"
    }
  ]
}
```

### 3. View one registration

`GET /registrations/:id`

Example: `GET /registrations/1`

- `200 OK` — registration found.
- `400 Bad Request` — ID is not a positive integer.
- `404 Not Found` — no registration exists with that ID.

### 4. View event capacity

`GET /event`

Example response:

```json
{
  "event": "Backend Development Workshop",
  "date": "2026-10-20",
  "capacity": 50,
  "registered": 1,
  "seatsRemaining": 49,
  "isFull": false
}
```

### 5. API overview

`GET /`

Returns a short API description, event information, and the available routes.

## How to test the API

You can use **Postman**, **Thunder Client** in VS Code, or `curl`.

Register a student:

```bash
curl -X POST http://localhost:3000/register \
  -H "Content-Type: application/json" \
  -d "{\"name\":\"Asha Kumar\",\"email\":\"asha@example.com\",\"collegeDepartment\":\"Computer Science\"}"
```

View all registrations:

```bash
curl http://localhost:3000/registrations
```

View one registration:

```bash
curl http://localhost:3000/registrations/1
```

Check event capacity:

```bash
curl http://localhost:3000/event
```

To test duplicate handling, send the same email twice. The second request should return `409 Conflict`. To test the capacity limit, register 50 different email addresses; a further registration should return `409 Conflict` with `"Event is full."`.

## Design decisions

- **SQLite:** keeps setup simple because a separate database server is not needed.
- **Unique email constraint:** prevents the same email from being registered more than once, even if capitalization differs.
- **Server-generated timestamp:** clients cannot choose or fake the registration time through the request body.
- **Transaction for capacity and insertion:** checks available capacity and inserts the registration as one database transaction, helping prevent overbooking when requests arrive close together.
- **Validation and status codes:** gives clients clear feedback for invalid input, duplicate registrations, full capacity, and missing registrations.

## Scope and limitations

This is a small recruitment-task project, not a production event-management platform. It does not include a frontend, login/authentication, organizer permissions, email notifications, or deployment configuration. The registration-list endpoint is intended for local task demonstration; a production service should protect participant details behind organizer authentication.
